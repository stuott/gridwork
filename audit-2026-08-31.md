### Bugs fixed

**The timer button broke on solve.** `renderStatus()` did
`this.timerToggleBtn.textContent = "Resume"` — but that button is an icon
button built by `iconButton()`. Assigning `textContent` deletes its `<svg>`
outright, so completing a puzzle replaced the pause icon with the bare word
"Resume" in the middle of an icon-only toolbar, and the button's `title` and
`aria-label` still said "Pause timer". Now uses `setButtonIcon(..., "play")`
and updates both labels, matching what the click handler already did. This is
leftover from the icon restructure that never got applied to this one path.

**Removing a puzzle from the recent list orphaned its saved grid.**
`main.ts` called `removeHistoryEntry()` but never `clearProgress()`. The
recent-puzzles list is the only route back to a puzzle, so every removal left
an unreachable `sudoku:progress:*` entry in localStorage forever.
`clearProgress()` existed and was used _only by a smoke test_. Now wired up.

**`favicon.svg` was a 0-byte file** that `index.html` links. Replaced with a
small grid mark.

### Config / process

**`strict` was never on.** `tsconfig.json` had `noUnusedLocals` and
`noUnusedParameters` but no `strict`, so no `strictNullChecks`, no
`noImplicitAny`. The whole codebase is _written_ to strict rules — non-null
assertions and optional chaining everywhere — but none of it was enforced;
`tsc` was checking far less than the code style implied. Verified `strict:
true` produces **zero** errors, and turned it on.

**Added `npm test`** running typecheck plus all five suites. Previously you
had to remember five separate commands, and nothing ran typecheck as part of
a composite.

**Stale doc references** in `fetchPuzzle.ts` (pointed at `vite.config.ts` and
an `npm run dev:web` script, neither of which exists here) and
`smoke-test-validate.ts`'s header comment (still listed only the Phase 3
constraints although the file now covers all of Phase 5).

## Part 2 — Outstanding issues, worst first

### 1. Jigsaw puzzles are silently validated against the wrong regions — RESOLVED 2026-08-31

`boxDims()` assumes square-root boxes, and `fpuzzles.ts` never reads the
per-cell `region` field that f-puzzles uses for irregular layouts. A jigsaw
puzzle therefore **imports cleanly, renders with 3×3 box lines, and
conflict-checks against boxes that are not its regions** — with no warning
anywhere. `phase-status.md` lists jigsaw under "not started", which is true
of support but understates the problem: the app doesn't decline the puzzle,
it quietly checks the wrong rule.

`scl.ts` handles the same situation far better — `regionsAreDefaultBoxes()`
explicitly distinguishes "regions restating the default boxes" from real
irregular ones and reports the latter as unsupported. `fpuzzles.ts` needs the
same guard as a minimum, even before real jigsaw support lands.

**Fixed.** `fpuzzles.ts` now has `hasIrregularRegions()`, reading the per-cell
`region` field and comparing *partitions* rather than region indexes (an
ordinary grid that numbers its boxes unusually must not be mistaken for a
jigsaw; partial or unreadable region data reads as irregular, the safe
direction to be wrong in). Both importers now set
`PuzzleModel.irregularRegions`, and the guard does more than report:
`boxesAreChecked()` in `model/types.ts` is the single gate every box-based
path goes through, so box conflicts and disjoint groups (`validate.ts`), box
elimination (`candidates.ts`), box units and pointing pairs (`hints.ts`), and
box outlines plus box peer-shading (`board.ts`) all switch off together. The
solver gets an import note saying rows and columns only are being checked.
Real jigsaw *support* — validating against the declared regions — is still
open, and is now a short step away since the layout is already being read.

### 2. scl `arrows` are dropped from the drawing entirely — RESOLVED 2026-08-31

`scl.ts` renders `lines`, `overlays` and `underlays` as unvalidated
decorations — the explicit contract being "draw the picture faithfully so a
human can apply the rules themselves". But scl's `arrows` array (it's in
PuzzleZipper's key table, so it's a real field) is not in `HANDLED_KEYS` and
is never parsed, so it's reported as unsupported and **never drawn**. An
arrow-variant SudokuPad puzzle renders with pieces of its picture missing,
which is the one failure mode the decorations channel exists to prevent.

**Fixed.** `parseDecorationArrows()` reads the array into a new
`SclDecorationArrow` (way-points plus color/thickness/headLength), `arrows`
is in `HANDLED_KEYS`, and `board.ts`'s `drawDecorationArrow()` draws the shaft
as a polyline plus a two-stroke open "V" head on the final way-point —
strokes rather than an SVG `<marker>`, so the head inherits the path's own
color and thickness and scales with zoom without a per-color def. Arrows also
count toward the board's shape total and the decoration overhang margin.
Still decorations, never constraints: nothing in the payload says an arrow
means the arrow-sum rule.

### 3. scl overlay `text` is discarded — RESOLVED 2026-08-31

`parseDecorationOverlays()` keeps `center`/`width`/`height`/colors and drops
the `text` field. Every number or letter SudokuPad draws on a board — killer
cage sums, X/V letters, little-killer clues, quadruple digits — renders as an
**empty shape with nothing in it**. Likely more common in practice than #2,
and the same contract violation.

**Fixed.** `text`, `fontSize` and `color` now come through on
`SclDecorationOverlay` and are drawn as a centered `<text>` (default half a
cell when the source omits a size). A second bug surfaced while fixing it:
the parser dropped any overlay without `width`/`height`, and SudokuPad writes
bare labels with neither — those are now kept, and the 0x0 shape behind them
is skipped so no stray dot appears.

**Open question, documented in code:** no payload on hand states the scale of
`fontSize` or an arrow's `headLength`. scl already mixes scales inside one
object (overlay `width`/`height` are cell fractions, `thickness` is cellSize
units), so `asCellFraction()` normalizes by magnitude — above 1.5 cells it is
read as cellSize units and divided. The two readings are far apart for every
plausible real value, and being wrong only mis-sizes a decoration rather than
mis-stating a rule. Replace it with a plain divide once a real arrow/text
payload settles the question.

### 4. A malformed constraint leaves the importer in a half-parsed state

`tryParse()` in both `fpuzzles.ts` and `scl.ts` catches, then pushes an
`unsupported` marker — but constraints already pushed **before** the throw
stay in the array. A payload with one bad cage among twelve yields eleven
enforced cages _plus_ a board note saying cages aren't supported. Both
statements are wrong. Fix is to snapshot `constraints.length` before `fn()`
and truncate back to it in the `catch`.

### 5. Starting to solve destroys unresumed progress

The board shows a "Resume progress saved …?" banner, but `afterEdit()` calls
`saveProgress()` on **every** edit. Ignore the banner, type one digit, and the
saved grid is overwritten with a near-empty one. The banner is offering
something the very next keystroke throws away. Suppress the save while a
resume offer is still pending, or write to a separate slot until it's answered.

### 6. f-puzzles cosmetic keys are reported as unsupported _constraints_

`KNOWN_KEYS` omits keys that appear in ordinary f-puzzles exports — `text`,
`circle`, `rectangle`, `line`, `cage`, `negative`. Anything unlisted becomes
an `unsupported` constraint, so the board's note line tells the solver their
puzzle uses constraint types the app can't enforce when several of those
entries are decorations. It overstates what's missing, which erodes trust in
the note exactly where the note needs to be believed. (Separately: unlike
scl, those f-puzzles decorations aren't drawn at all.)

### 7. `render/board.ts` has no test coverage — RESOLVED 2026-08-31

1,379 lines — the largest file in the project — and the only module with no
smoke test. Now covered by `scripts/smoke-test-board.ts` (`npm run test:board`,
91 checks) running against jsdom: structure and margins, pointer selection and
drag-paint, digit and pencil entry across multi-cell selections, highlights,
undo/redo, both shortcut guards, live-vs-on-demand conflict display,
auto-candidates, hints, win detection, save/resume, zoom, and teardown. The
timer-icon bug fixed above has an explicit regression test.

### 8. Every render does a full constraint scan

`render()` calls `findConflicts(model)` unconditionally — including when live
checking is **off** and the result is discarded — and `render()` runs on every
`pointermove` that changes the selection during a drag. So dragging across a
row re-scans every constraint and tears down and rebuilds the entire SVG once
per cell. Harmless at 9×9 today; it's the first thing that will bite on a
large or heavily-constrained board.

### Smaller notes

- Digit entry is gated on `e.key >= "1" && e.key <= "9"`, so a 16×16 grid can
  never receive digits above 9 even though `boxDims`/`validate` handle the size.
- Killer cages are only checked once **completely** filled — no "this cage
  already exceeds its sum" feedback, which is the normal solving affordance.
- `noUncheckedIndexedAccess` would cost ~168 errors, almost all of them
  index access in the smoke tests. Worth considering for `src/` alone.
- `ResolvedInput.kind` is populated and never read outside a test assertion.
- `SettingsModal` subscribes to verification prefs with no unsubscribe. Fine
  today (one instance, app lifetime), a leak if it ever becomes disposable.
- The settings modal doesn't trap Tab, so keyboard focus can wander behind
  the overlay.
